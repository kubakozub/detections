# detections

Sigma rules for what my WordPress finding leaves in the logs, with the log lines that
should and should not fire them, and the same rules rendered for Splunk, Elasticsearch
and Microsoft Sentinel / Defender.

The finding is HackerOne [#3931777](https://hackerone.com/reports/3931777): the lowest
role allowed to upload files could delete `wp-config.php` through the media finalize
route, and a WordPress without `wp-config.php` hands its installer to anyone (CVSS 9.9,
fixed in Gutenberg 23.8 and core [r63200](https://core.trac.wordpress.org/changeset/63200)
before 7.1 shipped). The write-up, with the replayed exploit, is at
[jakubkozub.com/research/wordpress-media-finalize](https://jakubkozub.com/research/wordpress-media-finalize/).

## Why there is no request signature

Every request in the chain is authenticated, authorised and successful: the Author holds
`upload_files`, owns the attachment, and WordPress printed the editor nonce to them.
Nothing 403s and nothing is malformed. The poisoned file name travels in a JSON body,
which an access log does not keep, and WordPress core has no audit log of its own. So
the rules look for a sequence, an outcome and a state change instead: one signal before
the impact, one at it, one after.

| Signal | Log source | Rule | Level |
|---|---|---|---|
| **Sequence.** One client finalizes an upload, then deletes media | web access log | [`web_wordpress_media_finalize_then_delete`](rules/web/web_wordpress_media_finalize_then_delete.yml), a temporal correlation of [`…finalize_request`](rules/web/web_wordpress_media_finalize_request.yml) and [`…delete_request`](rules/web/web_wordpress_media_delete_request.yml) | medium, hunt |
| **Outcome.** `wp-config.php` deleted | file-delete telemetry (EDR, Sysmon for Linux) | [`file_delete_lnx_wordpress_wp_config_deleted`](rules/linux/file_delete_lnx_wordpress_wp_config_deleted.yml) | high |
| | auditd | [`lnx_auditd_wordpress_wp_config_deleted`](rules/linux/lnx_auditd_wordpress_wp_config_deleted.yml) | high |
| | file-delete telemetry | [`file_delete_lnx_php_worker_outside_uploads`](rules/linux/file_delete_lnx_php_worker_outside_uploads.yml): the PHP worker deletes anything outside uploads, temp, sessions, caches and update staging | low, hunt |
| **Aftermath.** The installer answers 200 on a configured site | web access log | [`web_wordpress_installer_reachable`](rules/web/web_wordpress_installer_reachable.yml) | high |

The aftermath rule rests on one measured fact. On WordPress 7.0.3,
`/wp-admin/setup-config.php` answers 409 while `wp-config.php` exists; with the file
removed, every page answers 302 to the installer and the installer answers 200. An
access log does not record where a redirect points, but it does record that 200.

## Tests

```console
$ pip install -r requirements.txt
$ sigma check --fail-on-issues rules
$ python -m unittest discover -s tests -v
```

Nothing in the tests re-implements Sigma matching. Each rule is converted by pySigma's
SQLite backend, the same way a user would convert it, and the SQL runs over the fixture
events in an in-memory table. The correlation runs the same way: the backend generates
the windowed query and the test compares the alerts it raises.

- `tests/fixtures/webserver.jsonl`: the requests of the replayed exploit (REST with
  pretty and with plain permalinks, a `_method=DELETE` override, the classic admin
  delete link) next to ordinary editor traffic, scanners probing the installer, a
  delete without `force`, and a finalize the patched route rejects.
- `tests/fixtures/file_delete_linux.jsonl`, `auditd.jsonl`: synthetic events in the
  Sysmon for Linux and auditd formats, including the deployment and plugin-update
  deletions each rule documents as a false positive.
- Every fixture event names the rules that must match it; every other rule must not.

To check that the suite can fail, each of these changes was made on a copy and each
failed it: `/finalize` misspelled, the window cut to 1 minute, a filter emptied, the
status condition dropped from the installer rule, the auditd record type changed, and
the redirect status of the admin delete link changed.

## Renderings

`renderings/` is generated by `python scripts/render.py` with the backends pinned in
`requirements.txt`; rerun it after changing a rule.

| Target | Rules | Field names |
|---|---|---|
| Splunk SPL | all | web: as Splunk extracts them from `access_combined` (`clientip`, `method`, `uri_path`, `uri_query`, `status`); host: Sysmon for Linux, FileDelete events 23 and 26; auditd as recorded |
| Elasticsearch ES\|QL | web, file delete | Elastic Common Schema (`url.path`, `url.query`, `http.request.method`, `http.response.status_code`, `source.ip`; `file.path`, `process.executable`, `event.type: deletion`) |
| KQL | web, file delete | web: `AppServiceHTTPLogs`, where Azure App Service, WordPress on App Service included, writes its HTTP logs; host: Defender XDR `DeviceFileEvents`, `ActionType == "FileDeleted"` |

Every rendering was run against the same fixtures on the real engine: Elasticsearch
8.19.4, the Kusto emulator and Splunk 9.4.3 all return exactly the expected events
([`tests/engines/`](tests/engines/README.md)). Two things to know before using them:

- Add your own index, sourcetype or `from` pattern; the queries search everything.
- The SPL and ES|QL correlations come from the backends and count in fixed 15-minute
  buckets, so a pair that straddles a bucket boundary is missed. The Sigma rule means a
  sliding window, and the KQL correlation, assembled by `render.py` from the two filters
  the Kusto backend generated because that backend does not convert correlations, is a
  join that catches it.

## Tuning and blind spots

- Behind a reverse proxy or CDN, `c-ip` is the proxy. Group by the forwarded client
  address where the log records it.
- Both requests of the sequence carry the attachment id. If your pipeline extracts it,
  add it to the correlation's `group-by` and the hunt becomes a per-attachment join.
- Deletes from the grid-mode media library go through `admin-ajax.php` with the id in
  the body, and a method override sent as an `X-HTTP-Method-Override` header is not in
  the request line. Neither reaches an access log. The host-side rules still see the
  outcome.
- The rules match the URL encodings WordPress itself produces. Normalise URLs before
  matching if an attacker could choose an unusual one.
- `file_delete_lnx_php_worker_outside_uploads` is a hunt: core, plugin and theme updates
  and plugin removal delete files too. Suppress your maintenance windows, and exclude
  directories where your plugins keep state.
